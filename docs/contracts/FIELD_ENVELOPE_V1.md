# قرارداد پاکت رمزشده و محتوای ورودی، نسخه ۱

این قرارداد بین گوشی (FD-07)، فضای ابری (FD-06) و برنامه‌ی دسکتاپ (FD-01، FD-05) است.

## پاکت (envelope)

هر ورودی یک فایل JSON است با این فیلدها:

| فیلد | نوع | معنی |
|---|---|---|
| `v` | عدد | نسخه‌ی پاکت، فعلاً `1` |
| `kdf` | رشته | `scrypt` |
| `n`, `r`, `p` | عدد | پارامترهای scrypt، فعلاً `32768`، `8`، `1` |
| `salt` | base64 | نمک ۱۶ بایتی، تصادفی برای هر پاکت |
| `nonce` | base64 | ۱۲ بایت، تصادفی برای هر پاکت |
| `ct` | base64 | متن رمزشده‌ی AES-256-GCM همراه برچسب احراز هویت |

- کلید ۳۲ بایتی از عبارت عبور و `salt` با scrypt ساخته می‌شود.
- داده‌ی احراز هویت (AAD) رشته‌ی ثابت `barkav-field-envelope-v1` است.
- تغییر هر بایت یا عبارت عبور اشتباه باعث خطا می‌شود.

## محتوای داخل پاکت (payload، JSON)

### رسید (`kind = "receipt"`)

| فیلد | الزامی | معنی |
|---|---|---|
| `kind` | بله | `receipt` |
| `id` | بله | شناسه‌ی یکتای رسید (از گوشی) |
| `caption` | بله (می‌تواند خالی باشد) | توضیح کاربر، جدا از هر متن OCR |
| `received_at` | بله | زمان ثبت روی گوشی، ISO 8601 |
| `image_b64` | بله | بایت‌های JPEG بدون EXIF، base64 |

### گزارش روزانه (`kind = "daily_report"`)

| فیلد | الزامی | معنی |
|---|---|---|
| `kind` | بله | `daily_report` |
| `id` | بله | شناسه‌ی یکتای گزارش |
| `report_date` | بله | تاریخ گزارش، `YYYY-MM-DD` (شمسی یا میلادی، با برچسب) |
| `body` | بله | متن گزارش، فارسی (شرح گزارش) |
| `phase` | خیر | فاز ساخت، مثل `۱۴ - تیغه چینی` (از فهرست ۳۲ فاز) |
| `weather` | خیر | آب‌وهوا، مثل `آفتابی` |
| `temperature` | خیر | دما به درجه‌ی سانتی‌گراد، متن |

فیلدهای اختیاری خالی یا نبودن‌شان مشکلی ندارد؛ دیتابیس فقط مقدارهای پرشده را نگه می‌دارد.

### سند (`kind = "document"`، FD-13)

| فیلد | الزامی | معنی |
|---|---|---|
| `kind` | بله | `document` |
| `id` | بله | شناسه‌ی یکتای سند (از گوشی) |
| `mode` | بله | `quick` (ثبت سریع) یا `detailed` (ثبت با جزئیات) |
| `caption` | بله (می‌تواند خالی باشد) | شرح سند، مثل پیام تلگرام |
| `received_at` | بله | زمان ثبت روی گوشی، ISO 8601 |
| `images_b64` | بله | لیست JPEG به ترتیب، هر کدام base64، بدون EXIF؛ حداقل یکی |
| `review` | خیر | دسته‌بندی کامل: `title`، `transaction_type`، `document_kind` (`financial` یا `non_financial`)، و اختیاری `category`، `note` |

- سند `quick` بدون `review` می‌آید و در صف `new` می‌ماند.
- سند `detailed` با `review` کامل مستقیم `under_review` می‌شود. کامل نبودن `review` یعنی `new`.

### تصمیم بازبینی از گوشی (`kind = "review_decision"`، FD-12)

| فیلد | الزامی | معنی |
|---|---|---|
| `kind` | بله | `review_decision` |
| `item_id` | بله | شناسه‌ی سند (همان `id`) |
| `decision` | بله | `approve` یا `reject` |
| `decided_at` | بله | زمان تصمیم روی گوشی، ISO 8601 |

- تصمیم اول برنده است. تصمیمی که زودتر از سند برسد، دوباره امتحان می‌شود.
- تأیید فقط وضعیت را عوض می‌کند. هیچ ردیف مالی ساخته نمی‌شود.

## قواعد

- فایل‌های Drive نام معنی‌دار ندارند. نام فایل فقط شناسه‌ی تصادفی است.
- برنامه‌ی دسکتاپ هر ورودی را یک بار می‌خواند (`remote_id` دیده‌شده ثبت می‌شود).
- محتوای ناشناخته‌ی `kind` نادیده گرفته و گزارش می‌شود، نه اینکه خطا شود.
- تغییر ناسازگار در این قرارداد یعنی `v: 2`.
