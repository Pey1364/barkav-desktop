# قرارداد صندوق رسید و API، نسخه ۱

این سند قرارداد بین سه بخش است: صفحه‌ی گوشی (WR-05)، سرور (WR-02)، و صندوق فایل (WR-01). وارد کننده (WR-07) و آداپتور دسکتاپ (WR-08) هم به همین قرارداد تکیه می‌کنند. مقدار `schema_version` در هر `meta.json` برابر `1` است.

## چینش صندوق

```
<data>/web_receipts/inbox/
  <receipt_id>/
    receipt.jpg     عکس، JPEG، بدون EXIF، حداکثر ضلع ۲۴۰۰ پیکسل
    meta.json       فراداده‌ی رسید
```

`<receipt_id>` به این شکل است: `YYYYMMDD-HHMMSS-` و هشت نویسه‌ی هگزادسیمال (مثال: `20261014-120433-ea43809a`). سرور این نام را می‌سازد و از نام فایل ارسالی کاربر استفاده نمی‌کند.

## فیلدهای `meta.json`

| فیلد | نوع | الزامی | معنی |
|---|---|---|---|
| `schema_version` | عدد | بله | `1` |
| `receipt_id` | رشته | بله | شناسه‌ی یکتای رسید، همان نام پوشه |
| `caption` | رشته | بله (می‌تواند خالی باشد) | توضیح کاربر، حداکثر ۱۰۰۰ نویسه؛ هرگز با متن OCR مخلوط نمی‌شود |
| `received_at` | رشته | بله | زمان دریافت به شکل ISO 8601 با منطقه‌ی زمانی UTC |
| `state` | رشته | بله | `RECEIVED` یا `IMPORTED` |
| `source` | رشته | بله | فعلاً `web` |
| `pending_id` | رشته | بعد از ورود | شناسه‌ی ردیف صف تأیید |
| `imported_at` | رشته | بعد از ورود | زمان ورود به صف (UTC) |

## HTTP، نسخه‌ی ۱

| روش | مسیر | کار |
|---|---|---|
| GET | `/` | صفحه‌ی ثبت رسید (HTML فارسی راست‌چین) |
| GET | `/sw.js`، `/manifest.webmanifest`، `/icon-512.png` | دارایی‌های PWA |
| POST | `/api/v1/receipts` | ارسال یک عکس و توضیح |

### ارسال یک رسید

- بدنه: بایت‌های خام عکس. `Content-Length` الزامی است.
- هدر `Authorization: Bearer <کد جفت‌سازی>` الزامی است.
- هدر `Content-Type`: نوع عکس (`image/jpeg`، `image/png`، `image/webp`). اگر خالی باشد، محتوا بررسی می‌شود.
- هدر `X-Receipt-Caption`: توضیح، با `encodeURIComponent` به UTF-8 (اختیاری، حداکثر ۴۰۹۶ بایت پیش از رمزگشایی).

### پاسخ‌ها

| کد | معنی | بدنه |
|---|---|---|
| 201 | رسید ذخیره شد | `{"receipt_id": "..."}` |
| 400 | توضیح یا داده‌ی ارسال معتبر نیست؛ یا `Content-Length` صفر یا نامعتبر است | `{"error": "..."}` |
| 401 | کد جفت‌سازی اشتباه است (تأخیر یک‌ثانیه‌ای) | `{"error": "pairing code is wrong"}` |
| 404 | مسیر وجود ندارد | `{"error": "not found"}` |
| 411 | `Content-Length` نیست | `{"error": "content length is required"}` |
| 413 | عکس بیشتر از ۱۵ مگابایت است | `{"error": "image is too large"}` |
| 422 | فایل عکس خوانده نشد یا نوع آن پشتیبانی نمی‌شود | `{"error": "..."}` |

پاسخ‌ها هرگز متن عکس، کد جفت‌سازی یا مسیر فایل را برنمی‌گردانند.

## قاعده‌های سازگاری

- افزودن فیلد اختیاری به `meta.json` یا به پاسخ JSON، ناسازگار نیست. خواننده باید فیلدهای ناشناخته را نادیده بگیرد.
- تغییر نام فیلد، تغییر معنی، حذف فیلد یا تغییر کد خطا ناسازگار است. برای آن باید `schema_version: 2` و مسیر `/api/v2/` ساخته شود، و نسخه‌ی ۱ تا وقتی هیچ کاربری ندارد نگه داشته شود.
- وارد کننده فقط رسیدهایی را می‌خواند که `state == RECEIVED` دارند.

## قرارداد پورت صف (WR-06)

`add_receipt(receipt_id, caption, received_at, image_path, image_sha256) -> (pending_id, created)`

- برای هر `receipt_id` فقط یک ردیف صف ساخته می‌شود. فراخوانی دوباره `created=False` برمی‌گرداند و همان `pending_id` را.
- هیچ ردیف مالی نمی‌سازد.
- اگر خطا بدهد، وارد کننده رسید را `RECEIVED` نگه می‌دارد و دفعه‌ی بعد دوباره امتحان می‌کند.

## قرارداد دیتابیس برای رسید وب (DB-01 و DB-02)

| جدول | ستون یا مقدار | معنی |
|---|---|---|
| `pending_items` | `source = 'WEB'` | ردیف از کانال وب آمده است |
| `pending_items` | `external_ref = receipt_id` | کلید یکتای ایدمپوتنسی (شاخص یکتای جزئی) |
| `pending_items` | `telegram_chat_id = 0` | چت صفر هرگز چت واقعی تلگرام نیست (ADR-0001) |
| `pending_items` | `telegram_message_id` منفی و یکتا | شناسه‌ی جانشین برای زوج یکتای جدول |
| `pending_items` | `status = 'NEEDS_REVIEW'` | نیازمند بررسی انسانی |
| `receipt_analyses` | `provider = 'WEB_UPLOAD'`، `image_path`، `image_sha256` | مشخصات عکس؛ `ocr_text` خالی است تا OCR اجرا شود |
| `attachments` | `entity_type = 'PENDING'` | پیوست عکس به ردیف صف |

ردیف‌های تلگرام قبلی `source = 'TELEGRAM'` و `external_ref = NULL` می‌گیرند و هیچ تغییری نمی‌کنند.
